CASE STUDY · 2026.1 Patch 21

A sea-load FPS drop, traced to extra captain actors.

A targeted save edit restored normal performance in one long-running campaign. No game binaries or settings were changed. This report separates the measured cause from the origin that remains unknown.

A specific repair, with a specific boundary.

The companion tool addresses only the recognised extra-actor signature from this case. UBOAT can lose FPS for other reasons. A matching symptom alone is not enough to apply this repair.

01 / PLAYERS

Inspect first. Write a separate copy.

Use the Python script shipped with this report. The commands below use example filenames; replace them with your save paths. Keep your original save.

01

Inspect the save

Run the dry-run command. It analyses the file without writing a repaired save. Review the recognised actors and crew checks.

02

Create a new file

If the recognised signature and safety checks pass, choose a different output filename. The repair changes the activeSelf state of recognised extra actors while preserving the original file.

03

Restart once, then test

Fully close UBOAT before the first repaired load, especially if an affected original was already loaded. Start the game and load the new copy. Normal hot reloads of the repaired lineage worked in this case.

04

Save and reload normally

Make a new in-game save and check it again if needed. Record the game version, whether FPS improved, and the reported actor counts. Keep personal save files private unless you choose to share them.

Read-only inspection
python uboat_save_fps_fix.py "campaign.save" --dry-run
Separate repaired output
python uboat_save_fps_fix.py "campaign.save" --output "campaign.fixed.save" --json-report "repair.json"
Optional: use the Python API

Run this from a folder containing the tool, or make the module importable. Replace the example paths with files in an existing folder. inspect_save only reads; repair_save creates a separate save and JSON report when active recognised copies are found.

Python
from uboat_save_fps_fix import inspect_save, repair_save

source = r'C:\path\to\campaign.save'
report = inspect_save(source)
print(report['clones_active'], report['achievement_lockout'])

if report['clones_active']:
    result = repair_save(
        source,
        r'C:\path\to\campaign.fixed.save',
        json_report=r'C:\path\to\repair.json',
    )
    print(result['status'])

02 / EVIDENCE

What was actually observed

Tested build: 2026.1 Patch 21. Campaign originally created on 2024.1 Patch 2. This history alone does not establish the cause.

ObservationResult and limit
Performance symptomSea loads ran at about 15–25 FPS; leaving port could run normally. Pausing did not remove the slowdown.
Native sampling143 of 200 main-thread samples (71.5%) were in Unity NavMesh polygon queries. This identifies a sampled hotspot, not a universal frame-time percentage.
Managed caller stacksAll 17 recovered caller chains led through recursive NavMeshNavigator.SnapToNavMesh to NavMesh.SamplePosition, including the 6000 m recovery search.
Saved object graphTwo affected saves contained 32 and 64 active extra captain actors on World layer 16. None belonged to the actual 27-member crew or the real skipper reference.
Actual editOnly the owner GameObject activeSelf bytes of the recognised 32 or 64 extras were changed to false. Actors and references were retained; the real crew was untouched.
Player validationThe player reported normal FPS after repair. No controlled numerical after-repair benchmark was recorded.
Three save/load checksUser-created saves 10, 11 and 12 each retained 32 inactive extras, zero active extras and 27 active real crew. No growth or reactivation was found in these tests.
Achievement lockout auditAll 76 inspected .save files in this case had the campaign achievement-lockout flag set to false. This is not a test of 76 achievements or a guarantee of Steam awards.

Established in this case

The expensive recursive query path was observed at runtime. The extra actors were identified independently of the real crew. Deactivating only these actors resolved the reported symptom and survived the tested save/load cycles.

Still unknown

The original creator and trigger of the first extra actor were not proved. A cleanup gap may explain retention across loads. The observed 32 → 64 counts do not prove that every load creates or doubles copies.

03 / DEVELOPERS

A focused investigation target

This is one campaign and a save-only intervention, not a general reproduction across fresh campaigns or hardware. The useful next step is to trace actor ownership and expensive recovery queries together.

A / 6000 m

Profile the exact recovery branch

Count 6000 m SamplePosition attempts per navigator, recording layer, active state, crew membership and owner identity. Compare port departure, first sea load, pause and subsequent loads. Keep instrumentation bounded to avoid distorting the result.

B / 02

Audit the load lifecycle

The extras were outside PlayerCrew and lacked SceneObject; they shared a Character World Area parent. Compare cleanup ownership with what the serializer can retain. Treat incomplete cleanup as a hypothesis to test, not the proved first creation site.

C / 03

Preserve legitimate actors

Do not delete all World actors or all captain-named objects. Validate actual crew and skipper references, quest guests and dock NPCs. Any code fix should target ownership or the repeated recovery condition; the package does not install one.

04 / QUESTIONS

Before sharing or applying the repair

Will this fix every sea-load FPS problem?

No. It targets one recognised saved-object pattern. A no-match or failed validation should be treated as a reason to investigate another cause, not to broaden deletion rules.

What happens to achievements?

The tool preserves the original campaign lockout value, including true. It does not unlock a restricted campaign. The false values observed in this case do not guarantee Steam achievement delivery.

Are the extra characters deleted?

The repair deactivates their owner GameObjects. It keeps the saved objects and references. This avoids removing unknown graph links or touching genuine crew members.

Can the copies come back?

No growth or reactivation occurred in the three tested saves. The first creation trigger is still unknown, so permanent prevention across all game actions is not proved. Continue from the repaired lineage; an old affected save still contains its active copies.

How do I roll back?

Fully close the game and load your retained original save. The tool writes a separate output and does not patch game files. Progress made only in the repaired branch will not exist in the older original.

What should I share with developers?

Start with the game version, symptom, dry-run summary and this report. Save files may contain names and campaign history: share them only deliberately, preferably through a private channel requested by the developer.
